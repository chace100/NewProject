## 0. 结论速览

1. **渲染库选 Three.js**,不选 Babylon.js:同等"最小可玩场景"的实测产物 Three.js 比 Babylon.js 小约 **2.5 倍**(gzip 154 KB vs 380 KB),社区与示例体量大 4.4 倍(star 116k vs 26k),而本项目的渲染需求(低多边形地形、PBR 材质、方向光/阴影、第三人称跟随相机)两者都远超需求。
2. **物理方案选 cannon-es**,不选 Rapier / Ammo.js / 自写刚体:cannon-es 打进来只要 **gzip 36 KB**,API 是普通 JS 对象,可在 Node 里无渲染跑物理,天然满足"物理行为自动化测试";Rapier 更先进、维护更活跃,但 `rapier3d-compat` 内联 wasm 后 gzip **1.58 MB**(即使单独请求 `.wasm` 也要 gzip 1.11 MB),对一个"打开网页即玩"的初中生场景过重。
3. **物理精度只要求定性正确,但"定性正确"必须实测,不能推**:`d = v₀²/(2μg)` 是用来**选参数**的理想化依据(取 `μ_橡胶=0.9`、`μ_冰面=0.05` 得 18 倍余量),而 cannon-es 实际交付的是 **7.5 倍**(本节承接 review finding,详见 §1.5 的实测表)——仍高于"≥3 倍"的验收线,但必须由无渲染物理测试测出来。
4. **四条硬约束**(不遵守就会破坏教学意图或让测试变脆):①用单参数 `world.step(1/60)` 并把子步数当输入,三参数形式会按墙钟丢步;②角色必须带材质且 `friction = 1.0`,否则等效摩擦是**乘积**、被默认 0.3 打折;③不要用 `fixedRotation` 省掉滚动,实测它会系统性放大摩擦;④坡道角度必须实测标定,不能按 `tanθ ≤ μ` 设计。
5. **有 4 个可借鉴案例**(PhET、Poly Bridge / Bridge Constructor、Sonic / Super Mario 64 的冰面关、Algodoo),它们的共同手法是把"看不见的力"变成**屏幕上的箭头、数轴、颜色和慢放**——本卡把它们抽象为 3 条可迁移设计:即时力/速度可视化、失败点的具体归因、低成本重试。
6. **MVP 玩法循环**落在"预判闸门 → 有限加速度行动 → 距离数轴与幽灵轨迹 → 一键重试",5 关每关只引入一个新变量,依次覆盖牛顿第一定律(惯性)、摩擦力大小、速度与滑行距离的平方关系、惯性保持方向、综合应用。

## 1. 技术选型候选对比

### 1.1 测量方法与可复现命令

体积不是"包有多大",而是**用户首屏真正要下载多少**。本卡区分两类数字,并始终标明是哪一类:

- **发行产物(dist/build)**:包内实际发布的文件,原样量与 gzip —— 这是首屏真实传输量;
- **打包产物(bundled)**:tree-shaking + `esbuild --minify` 之后的结果 —— 这是应用最终会带上线的体积。

```bash
# 环境:node v24.21.0,esbuild 0.28.2,npm 11.19.1
mkdir -p /tmp/bench && cd /tmp/bench && npm init -y
npm i three@0.186.1 @babylonjs/core@9.30.0 cannon-es@0.20.0 \
      @dimforge/rapier3d-compat@0.21.0 ammo.js@0.0.10 esbuild

# 每个候选写一个"最小可玩场景"入口(src/*.js),再:
npx esbuild src/three-cannon.js --bundle --minify --format=esm --target=es2020 --outfile=out/three-cannon.js
gzip -9 -c out/three-cannon.js | wc -c

# 发行产物直接量:
gzip -9 -c node_modules/three/build/three.module.js | wc -c
```

"最小可玩场景"等价于跑酷 MVP 的下限:渲染器 + 场景 + 透视/跟随相机 + 一盏方向光 + 一块地面 + 一个角色方块 + 标准材质 + 一个刚体世界(地面刚体 + 角色刚体)。

> 注意:three@0.186.1 **不发布** minified build(`build/` 下只有 `three.module.js`、`three.core.js` 等)。CDN 上出现的 `three.module.min.js` 是 CDN 自己按需压缩生成的,不是包内容;#6 做首屏预算时应以发行产物 + 自己的打包结果为准。

**为什么"自写"没有胜出**:本项目的失败模式不是"算不准",而是"算得不直观"。自写方案在平面上很省,但关卡 5 要求"冰面 + 坡道 + 跳跃"组合,斜面接触、滑动摩擦与陡坡上的静态摩擦判定几乎必然要重写一遍动力学——等于用低风险换取高风险,而 cannon-es 拿到这些只需 36 KB。

### 1.4 明确推荐与理由

> **推荐:Three.js + cannon-es(单参数固定步长),外加一层约 100–200 行的"物理适配层"。**

理由,按优先级:

1. **首屏预算**:推荐栈的渲染 + 物理实测 **154 KB gzip**;Babylon.js + Havok 或 Three.js + Rapier 都要 ≥380 KB / 1.58 MB 量级。用户是"课后在浏览器里点开"的初中生,首屏每多 1 MB 都是真实的流失。
2. **测试可行**:cannon-es 能在 Node 里无渲染运行,物理行为可以写成确定性单元测试(见 §1.5),这正是 #6 要求的"物理行为自动化测试怎么写"的前置条件。
3. **精度够用且可证**:教学要求的"摩擦/惯性定性正确"在 cannon-es 上是**可测**的,但**不是可直接推导的**(§1.5 给出实测值与两条必须写进 #6 的硬约束)。
4. **生态与资料**:Three.js 的示例基数与中文教程量最大;cannon-es 是 `three/examples/jsm/physics/*` 的既有邻域,遇到问题能搜到答案。
5. **可替换**:维护风险用适配层对冲。适配层只暴露 `createWorld / addBody / step / getTransform / setFriction`,把 cannon-es 换成 Rapier 的工作量可控在一天内。

### 1.5 物理建模方案与引擎实测

只做教学游戏,不做物理模拟器,所以取舍原则是"玩家能感知到的量必须正确,感知不到的量交给引擎"。但**"交给引擎"的部分必须实测**,下表每一项都给出实测结论。

测量方法:用 Node 直接跑 cannon-es `0.20.0`(无渲染、无 WebGL),每个场景都是"1 kg 立方体(半边长 0.5 m)+ 静态地面/斜面",角色与地面都使用显式 `Material`,`world.step(1/60)` 单参数推进。脚本见 §6。

#### (a) 决定性:必须用单参数 `world.step(1/60)`

cannon-es 的 `step(dt, timeSinceLastCalled, maxSubSteps)` 在传了第二个参数时进入**累加器 + 墙钟**分支(`dist/cannon-es.js:12510-12549`):

```js
if (timeSinceLastCalled === undefined) {
  this.internalStep(dt);          // 纯固定步:结果只由调用次数决定
  this.time += dt;
} else {
  this.accumulator += timeSinceLastCalled;
  const t0 = performance.now();
  let substeps = 0;
  while (this.accumulator >= dt && substeps < maxSubSteps) {
    this.internalStep(dt); this.accumulator -= dt; substeps++;
    if (performance.now() - t0 > dt * 1000) break;   // 慢机器上直接丢弃
  }
  this.accumulator = this.accumulator % dt;          // 余数被抹掉
  // ...再写 interpolatedPosition(渲染插值)
}
```

后果:同样的初始条件、同样的**墙钟时长**,帧率不同的机器实际执行的子步数不同。实测(μ=0.9 平面上 5 m/s 的箱子,3 s 墙钟):

| 调用方式 | 帧率 | 实际子步数 | `world.time` | 位置 x |
| --- | --- | --- | --- | --- |
| `world.step(1/60, Δt, 3)` | 60 fps | 180 | 3.000 s | 0.7390 |
| `world.step(1/60, Δt, 3)` | 30 fps | 180 | 3.000 s | 0.7390 |
| `world.step(1/60, Δt, 3)` | 10 fps | 90 | 3.000 s | 0.3710 |
| `world.step(1/60, Δt, 3)` | 5 fps | 45 | 3.000 s | 0.1871 |
| `world.step(1/60)` × 180 次 | — | 180 | 3.000 s | 0.7390(重复运行逐位一致) |

**约束**:用 `world.step(1/60)`,由调用方(游戏循环或测试)自己决定每帧/每次运行推进几个子步,并把子步数当作**输入的一部分**记录;`world.time` 在三参数形式下会与实际模拟进度脱节,不能当计时器或断言依据。

#### (b) 摩擦的等效系数是**乘积** `μ_地面 × μ_角色`

`createFrictionEquationsFromContact`(`dist/cannon-es.js:10448-10453`)在两侧材质都带摩擦值时用乘积覆盖接触材质:

```js
let friction = cm.friction;
const matA = shapeA.material || bodyA.material;
const matB = shapeB.material || bodyB.material;
if (matA && matB && matA.friction >= 0 && matB.friction >= 0) {
  friction = matA.friction * matB.friction;   // 乘积,不是取某一侧
}
```

角色若不显式指定材质,会落到 `defaultContactMaterial.friction = 0.3`,等效摩擦被"打折"。实测(地面 μ=0.05,5 m/s,5 s 位移):

| 角色材质摩擦 | 等效 μ | 冰面 5 s 滑行 |
| --- | --- | --- |
| `1.00`(推荐) | 0.05 | 9.21 m |
| `0.30`(cannon 默认) | 0.015 | 14.73 m |

**约束**:角色必须显式挂一个 `Material`,`friction = 1.0`,让"地面摩擦系数"就是设计值;`restitution` 同理(也是乘积)。

#### (c) 摩擦上限按 `μ·|g|` 缩放,不按接触法向力;实测比值 ≠ 理论比值

同一函数的下一行:`mug = friction * (world.frictionGravity || world.gravity).length()` —— 上限来自**重力大小**,没有乘 `cosθ`,也不随法向力缩放,而且摩擦力沿两个切向各建了一个方程、各自带这个上限。

实测(角色材质 1.0,即等效 μ = 地面 μ,v₀ = 5 m/s,5 s 位移):

| 配置 | 冰面 μ=0.05 | 橡胶 μ=0.90 | 实测比 | 库仑理想比 |
| --- | --- | --- | --- | --- |
| 自由旋转,`solver.iterations=10` | 9.21 m | 1.23 m | **7.49** | 18.0 |
| 自由旋转,`solver.iterations=50` | 9.15 m | 1.13 m | 8.11 | 18.0 |
| `fixedRotation = true`,`iterations=10` | **0.10 m** | **0.01 m** | 12.97 | 18.0 |

由此得到三条必须写进 #6 的结论:

1. `d = v₀² / (2μg)`(比值 = `μ_橡胶/μ_冰` = 18)只用于**选参数**;引擎实际交付 **≈7.5×**,仍高于"≥3 倍"的验收线,但**验收断言必须测出来**,不能由公式推算。
2. `fixedRotation = true` 不是"只会跑、不会滚"的免费开关:实测冰面 5 m/s 的箱子 5 s 只走 **0.10 m**,摩擦被系统性放大一个数量级,手感会完全失真。
3. 坡道:自由旋转的箱子实测在 **44°–45° 之间**释放(真实库仑 `atan(0.9) = 42.0°`,相差 2–3°,可接受);但 `fixedRotation` 下 **66°、75°、80° 仍不下滑**(真实应 42° 释放)。摩擦上限不按法向分量缩放,所以**坡道静摩擦阈值不是 `tanθ ≤ μ`**。

#### (d) 惯性、匀速直线、跳跃

| 现象(教学点) | 建模方式 | 怎么验证 |
| --- | --- | --- |
| 惯性:不受水平力时保持匀速直线运动 | 引擎刚体 + **显式把 `linearDamping` / `angularDamping` 置 0**(cannon-es 默认都是 `0.01`,不清零会得到"永远在减速"的错觉) | 无摩擦平面、无输入时连续 5 s,速度衰减 < 0.1%,方向偏角 < 0.1° |
| 匀速直线运动(合力为零) | 竖直方向重力与支持力由接触约束抵消,水平方向无外力 | 直道段位置误差在 5 s 内 < 1%(与解析解 `x = v₀t` 对比) |
| 速度越大越难停 | 由 `d ∝ v₀²` 关系涌现,不需要额外实现 | 初速翻倍,滑行距离实测 ≈ **4 倍**(在固定子步数下测量,方差不超 ±10%) |
| 跳跃与抛物线 | 引擎重力积分 | 跳跃远度与水平初速成正比 |
| **必须自写、不许偷懒的部分:角色控制层** | 输入只映射为**有限加速度**(并 clamp 最大加速度),**禁止直接 `body.velocity.set(...)`** | 若直接设速度,惯性直觉立刻消失:同一次"松手"在不同速度下都瞬间停下,关卡 3/4 的教学意图被破坏 |
| 决定性 | `world.step(1/60)` 单参数 + 自定义子步计数 + 关闭随机 | 同一子步数下两次运行结果**逐位一致**(见 (a) 实测) |

已知限制(交给 #6 记住):cannon-es 不建模滚动摩擦与空气阻力;默认 `GSSolver` 迭代次数少、求解结果对迭代次数敏感(见 (c) 表的 7.49 vs 8.11);`cannon-es` 自 2022 年起没有新发布,应把版本号写死并保留适配层。

### 1.6 被否决项的一句话理由

- **Babylon.js**:体积 2.5 倍,而它相对 Three.js 的增量能力(内置相机、GUI、Inspector、Node Material)对本项目的低多边形跑酷都不是瓶颈;V1/V2 双物理插件体系还会在 #6 引入不必要的决策。
- **Rapier**:工程上更优,但 1.11–1.58 MB gzip 的 wasm 与"打开即玩"冲突;保留为关卡数量/动态物体数量上升后的升级路径。
- **Ammo.js**:体积 1.56 MB 且无法 tree-shake,Emscripten API 样板多,维护节奏与 npm 脱节。
- **自写简化刚体**:平面场景够用,但无法低成本覆盖关卡 5 的"冰面 + 坡道 + 跳跃",性价比低于 36 KB 的 cannon-es。

## 2. 可借鉴案例及其可迁移设计

四个案例都不是"因为好玩"才被选中,而是各自解决了一个本项目会撞上的问题:怎么让力**可见**、怎么让失败**有信息量**、怎么让重试**没有心理成本**。

### 2.1 PhET Interactive Simulations(美国科罗拉多大学,免费中学物理交互模拟;参考「力和运动:基础」「斜坡:力和运动」)

它把力画出来:屏幕上每个物体带**实时力矢量箭头**,旁边跟**数值读数**和速度/加速度图;摩擦可以用滑块调,还能一键切到"冰面"场景;多个模拟内置**预测式提问**(先让学生猜,再运行)。

可迁移到本项目的设计:

- **HUD 可视化层**:角色头顶常驻"速度箭头 + 惯性条",把"我现在有多难停下来"变成可见量,而不是玩家的肌肉记忆。
- **参数旋钮**:通关后解锁摩擦/重力滑块,让学生自己复现现象(与 §3.2 的"自主感"对应)。
- **预测式提问**:PhET 用弹窗提问,本项目要改成**关卡内的动作**(§3.1 的"预判闸门"),避免打断跑酷节奏。

### 2.2 Poly Bridge / Bridge Constructor(桥梁建造沙盒)

循环是"设计 → 释放负载 → 看结果 → 改一处 → 再释放"。关键是**失败有具体归因**:构件应力用颜色梯度显示,先断的那根被高亮,而不是只告诉你"桥塌了";重试是秒级的,沙盒模式还取消了造价压力。

可迁移到本项目的设计:

- **失败点归因**:撞墙时高亮"接触点 + 那一刻的速度值",明确告诉学生"你是停不下来,不是跳得不够"。
- **秒级重试**:一键重来,重启 < 1 s,不做失败动画惩罚——与本项目"失败是物理后果,不是扣分"的定位一致。
- **双模式分层**:沙盒(自由实验,无目标)与挑战(星级)分离,对应本项目的"自由实验场 + 5 关卡"。

### 2.3 Sonic the Hedgehog 系列 / Super Mario 64 的冰面关(Ice Cap Zone / Cool, Cool Mountain)

商业跑酷游戏早就在用"摩擦系数"当关卡设计语言:冰面上加速与刹车距离显著变长,玩家必须**提前**做动作,否则就会滑出边缘或撞墙;速度感用镜头 FOV、音效与运动模糊放大。这里最有价值的一点是:**失败被视为理所当然的物理结果**,玩家不会觉得被惩罚,而是觉得"我早该想到"。

可迁移到本项目的设计:

- **地形即教具**:冰面/橡胶地用颜色 + 反光 + 脚步声区分,让学生不靠文字就能读出摩擦系数。
- **速度的体感化**:镜头 FOV 随速度线性拉伸 + 风声/脚步声加快,让"速度积累"变成紧张感,而不是数字。
- **无惩罚失败**:与 §2.2 的"秒级重试"合并执行,不设生命值/分数惩罚。

### 2.4 Algodoo(瑞典 Algoryx,面向中学课堂的 2D 物理沙盒)

它提供实时可改的重力/摩擦/阻尼、**慢动作回放**与**轨迹追踪**,教师在课堂上用它做"改一个参数,看结果怎么变"的探究。

可迁移到本项目的设计:

- **失败慢放**:撞墙瞬间 0.3× 慢放 1.5 s,让学生看清"不是操作慢了,是惯性没被抵消"。
- **幽灵轨迹**:显示上一次尝试的路径,失败原因和修正方向同时可见(§3.1 第 3 拍)。
- **探究式作业**:参数面板可作为延伸任务("把重力调成 3 m/s²,通关还能成立吗?"),把游戏寿命延长到课后。

## 3. MVP 玩法循环建议

### 3.1 "预判 → 行动 → 看结果 → 修正"的具体落地

| 拍 | 设计 | 必须遵守的约束 |
| --- | --- | --- |
| 1. 预判 | 关卡关键点前设"**预判闸门**":2 选 1 的快速选择(例:"冰面段会在 A 点还是 B 点停下?"),用画面内浮标 + 左右方向键/点击完成,选完立即继续跑 | 出现在动作前 ≤10 m 处;不弹窗、不暂停;必须选完才能通过闸门(强制进入"先想后做"的心智状态) |
| 2. 行动 | 跑酷操作只有三个动作:**向前加速**(按住)、**刹车/减速**(按住)、**跳跃**(单击),键位与手柄映射由 #6 定稿;输入只产生**有限加速度**并 clamp 上限 | 禁止直接设置速度;镜头、音效随速度线性增强 |
| 3. 看结果 | 停下/撞墙瞬间给出三组证据:(a) 实际滑行距离的**数轴读数(米)**与预判刻度同屏对比;(b) 上一次尝试的**幽灵轨迹**;(c) **0.3× 慢放 1.5 s** | 证据先于结算页出现;数值保留一位小数,避免"精确到厘米"的过度严谨 |
| 4. 修正 | 一键重试(≤1 次按键/点击),重启 < 1 s,保留幽灵轨迹与上一次预判选择 | 不扣资源、不播失败动画;结算文案指向"哪儿不一样",不指向"你错了" |

### 3.2 青少年玩家心理映射

| 心理需求 | 落地手段 | 可检查的指标 |
| --- | --- | --- |
| 即时反馈 | 任何输入到可见反馈 < 300 ms(音效/粒子/速度线);失败到可重试 < 1 s | 手动测 3 个关键动作 |
| 进度感 | 顶部 5 关进度条;每关 1–3 星(由"预判正确次数 + 尝试次数"决定);本地保存最佳滑行距离 | 刷新页面进度不丢(无后端,localStorage) |
| 挑战梯度 | 每关只引入一个新变量(见 §3.3);容差从关 1 的 ±1.5 m 收紧到关 5 的 ±0.4 m | 目标:首次通关尝试次数中位数 2 次 |
| 失败脱敏 | 无生命值、无扣分、无失败动画;文案用"再试一次,看看哪儿不一样" | 单关失败后再次尝试率(本地埋点可后置) |
| 自主感 | 通关解锁摩擦/重力实验旋钮;自由实验场(无目标) | 学生能自行复现"冰面 vs 橡胶地"对比 |

### 3.3 5 关知识点排布(人教版八年级下册第 8 章「运动和力」)

| 关 | 名称 | 知识点 | 本关新引入的变量 | 玩家要做的事 | 过关判定 | 典型失败 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 起跑与刹车 | 8.1 力是改变物体运动状态的原因 | 摩擦力(单一橡胶地) | 加速到终点线前主动刹车,恰好停在目标区 | `\|x - x_目标\| ≤ 1.5 m` 且越线不超过 1.5 m | 冲过线 / 差一截没到 |
| 2 | 冰面还是橡胶地 | 8.3 摩擦力大小与接触面粗糙程度有关 | 路面材质(μ 切换) | 先选"哪一段滑得更远",再通过冰面段并在指定区停住 | 冰面段末端停在目标区 | 冰面上刹不住、撞墙 |
| 3 | 速度翻倍 | 8.1 力是改变物体运动状态的原因 + **滑行距离与速度的平方成正比**(`d ∝ v₀²`) | 初速(加速时长) | 先回答"速度翻倍,那么滑行距离大约变成几倍?",再通关 | 选择"4 倍"且实际距离落在目标区 | 低估滑行距离(选 2 倍) |
| 4 | 直着飞出去 | 8.1 惯性:物体保持原来的运动方向 | 弯道 / 断崖(方向变化) | 提前转向过弯,或故意利用惯性直线飞越缺口 | 落到对岸平台 | 撞弯道外壁 / 掉进缺口 |
| 5 | 综合路线 | 8.1 + 8.3 综合 | 组合(冰面 + 坡道 + 跳跃) | 一次跑完多段摩擦路线,中途 1 个预判闸门 | 全程 0 次越线失控 且 预测正确 ≥1 次 | 任一环节失控 |

设计原则:每一关只有**一个**新变量,其余参数与上一关一致;这样"结果变了"必然可以归因到"这个变量变了",教学因果链不会被多个变量污染。

> 用词提醒:惯性大小只由**质量**决定,与速度无关;速度变大改变的是"停下来需要的距离/时间",不是"惯性变大"。关卡 3 的知识点列必须按上表写法,不要写"惯性大小与速度有关"——那正是本关要纠正的错误直觉。

### 3.4 关卡参数示例(交给 #6 校验与定稿)

| 参数 | 建议值 | 依据 |
| --- | --- | --- |
| `μ_橡胶` | 0.90 | 与 `μ_冰面` 之比 ≥3 的余量要求 |
| `μ_冰面` | 0.05 | 库仑理想比 `0.90/0.05 = 18`;**实测比约 7.5**(§1.5(c)),仍 ≥3 |
| 角色材质 `friction` | **1.00**(必须显式指定) | 等效摩擦是**乘积** `μ_地面 × μ_角色`(§1.5(b));留默认 0.3 会让地面参数失去意义 |
| 角色材质 `restitution` | 0.00 | 同为正乘积语义;教学关不需要弹跳 |
| `linearDamping` / `angularDamping` | **0.00** | cannon-es 默认 0.01,不清零则"惯性"被静默衰减 |
| 重力 | 9.82 m/s² | 与教材一致 |
| 角色水平初速上限 | 12 m/s | 让"速度翻倍"(6 → 12)在关卡 3 中可体验 |
| 物理步进 | `world.step(1/60)` 单参数;子步数由调用方计数并记录 | 三参数形式按墙钟丢步,结果不可复现(§1.5(a)) |
| `solver.iterations` | 10(定稿后写死) | 求解结果对它敏感:同一场景 10 与 50 次迭代的实测比是 7.49 vs 8.11(§1.5(c)) |
| 坡道角度(关卡 5) | **由测试标定**(先按 15°–25° 设计并断言释放/静止行为) | 摩擦上限按 `μ\|g\|` 不按法向分量,阈值不是 `tanθ ≤ μ`;`fixedRotation` 下 66°–80° 都不下滑(§1.5(c)) |
| `fixedRotation` | **禁止使用** | 实测冰面上 5 m/s 的箱子 5 s 只滑 0.10 m,摩擦被系统性放大(§1.5(c)) |
| 静止判定阈 | 0.05 m/s | 避免刚体永远"几乎为零"地漂移 |
| 过关容差 | 关 1 ±1.5 m → 关 5 ±0.4 m | 挑战梯度 |
| 首屏加载预算 | JS + WASM ≤ 400 KB gzip | 推荐栈实测 154 KB,余量留给关卡资源与 UI |

## 5. 风险与开放问题(交给 #6 决策)

1. **cannon-es 维护停滞**(最后一次 npm 发布 2022-08-12,仓库最后 push 2024-01-06)。缓解:锁定精确版本号 + 物理适配层;若 #6 判断长期风险不可接受,升级到 Rapier 的代价是首屏 +1.11 MB gzip。
2. **求解器敏感**:同一个场景,`solver.iterations` 从 10 改到 50,橡胶地滑行距离实测从 1.23 m 变成 1.13 m(比值 7.49 → 8.11)。#6 必须把求解器参数与步进方式写死,否则"同一操作、同一结果"这条教学承诺会漂移。
3. **步进与帧率解耦**:三参数 `step()` 在低帧率机器上会静默丢弃模拟步(5 fps 时 3 s 墙钟只跑 45 子步,见 §1.5(a))。若 #6 直接照搬官方示例的 `world.step(1/60, dt, 3)`,CI 上会出现"同一断言时通时不通"的 flaky 测试,学生之间也会得到不同的滑行距离。
4. **坡道不能靠公式**:摩擦上限按 `μ|g|` 而非法向分量,且 `fixedRotation` 会让物体在 66°–80° 的坡上都不下滑(§1.5(c))。关卡 5 的坡道角度需要逐个测试标定。
5. **低端设备性能**:桌面浏览器优先,但学校机房可能是集显。建议 #6 明确降级策略(默认关阴影/降低像素比/固定 30 FPS 选项);注意降帧率**不会**改变物理结果,只要用单参数步进。
6. **真实性与可玩性的冲突**:完全真实的摩擦会让学生"永远停不下来"。上限由 `μ` 和过关容差控制,教学文案不承诺"这是真实路面"。
7. **"直接设速度"的诱惑**:任何为了手感而直接给刚体赋值速度的实现,都会破坏本项目的核心教学意图,建议在 #6 写成硬约束。
8. **关卡数据格式**:地形段 / 摩擦系数 / 起点终点 / 过关判定 / 教学文案挂载点的 JSON schema 由 #6 定义;本卡只要求"摩擦系数与关卡内容解耦,加关卡不改引擎代码"。
9. **教学文案用词**:需要与学校教材口径一致(例如"惯性"只由质量决定,与速度无关,见 §3.3 的用词提醒)。建议人工/教师复核一次,这是唯一需要 human-in-the-loop 的点。

### 6.3 物理实测环境与脚本

```bash
mkdir -p /tmp/cannonlab && cd /tmp/cannonlab && npm init -y
npm i --no-audit --no-fund cannon-es@0.20.0
node exp.mjs      # 场景:1 kg 立方体(半边长 0.5 m)+ 静态地面/斜面
```

场景构造要点(与 §1.5 各表一一对应):

- 地面/斜面:`mass = 0`,形状为 `Plane`(平面)或 `Box(30, 0.5, 30)`(斜面 `setFromEuler(0, 0, θ)`),带显式 `Material` 与 `friction`;
- 角色:`mass = 1`,`Box(0.5, 0.5, 0.5)`,带显式 `Material`(`friction` 取 1.0 或 0.3),`linearDamping = angularDamping = 0`;
- 推进:`world.step(1/60)` 单参数,60 次/s;位置取 `body.position`,`速度取 `body.velocity.length()`;
- 决定性对比:同一场景分别以 60/30/10/5 fps 的 `Δt` 调用 `world.step(1/60, Δt, 3)`,对比 `world.stepnumber`(实际子步数)与最终位置;
- 源码引用行号对应 `cannon-es@0.20.0` 的 `dist/cannon-es.js`(`step()` 12510-12549;`createFrictionEquationsFromContact()` 10448-10459)。

说明:体积为"最小可玩场景"的实测值,不包含关卡美术资源、音效与字体;真实首屏预算需在 #6 中连同资源一起核算。案例描述(§2)为公开产品的设计手法归纳,不含其源码或素材。
