## 0. 结论速览

1. **渲染库选 Three.js**,不选 Babylon.js:同等"最小可玩场景"的实测产物 Three.js 比 Babylon.js 小约 **2.5 倍**(gzip 154 KB vs 380 KB),社区与示例体量大 4.4 倍(star 116k vs 26k),而本项目的渲染需求(低多边形地形、PBR 材质、方向光/阴影、第三人称跟随相机)两者都远超需求。
2. **物理方案选 cannon-es**,不选 Rapier / Ammo.js / 自写刚体:cannon-es 打进来只要 **gzip 36 KB**,API 是普通 JS 对象,可在 Node 里无渲染跑物理,天然满足"物理行为自动化测试";Rapier 更先进、维护更活跃,但 `rapier3d-compat` 内联 wasm 后 gzip **1.58 MB**(即使单独请求 `.wasm` 也要 gzip 1.11 MB),对一个"打开网页即玩"的初中生场景过重。
3. **物理精度只要求定性正确,但"定性正确"必须实测,不能推**:`d = v₀²/(2μg)` 是用来**选参数**的理想化依据(取 `μ_橡胶=0.9`、`μ_冰面=0.05` 得 18 倍余量)。**引擎自带的接触摩擦交付不了这个对比**:按 §6.3 的场景实测,自由旋转的立方体在冰面与橡胶地上的滑行距离是 1.0827 m vs 1.0154 m,比值 **1.07**——低于本卡自己的"≥3 倍"验收线(§1.5(c))。因此摩擦必须由**适配层显式施加**(§1.5(d):实测 18.52 倍)。
4. **四条硬约束**(不遵守就会破坏教学意图或让测试变脆):①用单参数 `world.step(1/60)` 并把子步数当输入,三参数形式会按墙钟丢步;②角色必须带材质且 `friction = 1.0`,否则等效摩擦是**乘积**、被默认 0.3 打折;③摩擦与坡道释放必须走适配层的库仑冲量,**不能依赖引擎接触摩擦**——它既交付不了 μ 的对比,也不会在 `tanθ > μ` 时释放(实测 75° 仍不下滑);④地面必须比 `d_冰面(12 m/s) = 146.5 m` 更长,`Box(30, 0.5, 30)` 不够。上表里的每个数字都能用仓库内的 `docs/research/exp.mjs` 重跑复现(§6.3)。
5. **有 4 个可借鉴案例**(PhET、Poly Bridge / Bridge Constructor、Sonic / Super Mario 64 的冰面关、Algodoo),它们的共同手法是把"看不见的力"变成**屏幕上的箭头、数轴、颜色和慢放**——本卡把它们抽象为 3 条可迁移设计:即时力/速度可视化、失败点的具体归因、低成本重试。
6. **MVP 玩法循环**落在"预判闸门 → 有限加速度行动 → 距离数轴与幽灵轨迹 → 一键重试",5 关每关只引入一个新变量,依次覆盖牛顿第一定律(惯性)、摩擦力大小、速度与滑行距离的平方关系、惯性保持方向、综合应用。

## 1. 技术选型候选对比

### 1.1 测量方法与可复现命令

体积不是"包有多大",而是**用户首屏真正要下载多少**。本卡区分两类数字,并始终标明是哪一类:

- **发行产物(dist/build)**:包内实际发布的文件,原样量与 gzip —— 这是首屏真实传输量;
- **打包产物(bundled)**:tree-shaking + `esbuild --minify` 之后的结果 —— 这是应用最终会带上线的体积。

```bash
# 环境:node v24.21.0,esbuild 0.28.2,npm 11.19.1
mkdir -p /tmp/bench && cd /tmp/bench && npm init -y
npm i three@0.186.1 @babylonjs/core@9.30.0 cannon-es@0.20.0 \
      @dimforge/rapier3d-compat@0.21.0 ammo.js@0.0.10 esbuild

# 每个候选写一个"最小可玩场景"入口(src/*.js),再:
npx esbuild src/three-cannon.js --bundle --minify --format=esm --target=es2020 --outfile=out/three-cannon.js
gzip -9 -c out/three-cannon.js | wc -c

# 发行产物直接量:
gzip -9 -c node_modules/three/build/three.module.js | wc -c
```

"最小可玩场景"等价于跑酷 MVP 的下限:渲染器 + 场景 + 透视/跟随相机 + 一盏方向光 + 一块地面 + 一个角色方块 + 标准材质 + 一个刚体世界(地面刚体 + 角色刚体)。

> 注意:three@0.186.1 **不发布** minified build(`build/` 下只有 `three.module.js`、`three.core.js` 等)。CDN 上出现的 `three.module.min.js` 是 CDN 自己按需压缩生成的,不是包内容;#6 做首屏预算时应以发行产物 + 自己的打包结果为准。

**为什么"自写"没有胜出**:本项目的失败模式不是"算不准",而是"算得不直观"。自写方案在平面上很省,但关卡 5 要求"冰面 + 坡道 + 跳跃"组合,斜面接触、滑动摩擦与陡坡上的静态摩擦判定几乎必然要重写一遍动力学——等于用低风险换取高风险,而 cannon-es 拿到这些只需 36 KB。

### 1.4 明确推荐与理由

> **推荐:Three.js + cannon-es(单参数固定步长),外加一层约 100–200 行的"物理适配层"。**

理由,按优先级:

1. **首屏预算**:推荐栈实测 **154 KB gzip**——这是**渲染 + 物理打包在一起的整个最小可玩场景**,精确值 157,228 B gzip(§1.2);其中物理库 cannon-es 单独只占 **36 KB gzip**(§1.3)。同口径下 Babylon.js + Havok 或 Three.js + Rapier 都要 ≥380 KB / 1.58 MB 量级。用户是"课后在浏览器里点开"的初中生,首屏每多 1 MB 都是真实的流失。
2. **测试可行**:cannon-es 能在 Node 里无渲染运行,物理行为可以写成确定性单元测试(见 §1.5),这正是 #6 要求的"物理行为自动化测试怎么写"的前置条件。
3. **精度够用且可证**:教学要求的"摩擦/惯性定性正确"在 cannon-es 上是**可测**的,但**不是可直接推导的**(§1.5 给出实测值与两条必须写进 #6 的硬约束)。
4. **生态与资料**:Three.js 的示例基数与中文教程量最大;cannon-es 是 `three/examples/jsm/physics/*` 的既有邻域,遇到问题能搜到答案。
5. **可替换**:维护风险用适配层对冲。适配层只暴露 `createWorld / addBody / step / getTransform / setFriction`,把 cannon-es 换成 Rapier 的工作量可控在一天内。

### 1.5 物理建模方案与引擎实测

只做教学游戏,不做物理模拟器,所以取舍原则是"玩家能感知到的量必须正确,感知不到的量交给引擎"。但**"交给引擎"的部分必须实测**,下表每一项都给出实测结论。

测量方法:用 Node 直接跑 cannon-es `0.20.0`(无渲染、无 WebGL),每个场景都是"1 kg 立方体(半边长 0.5 m)+ 静态地面/斜面",角色与地面都使用显式 `Material`,`world.step(1/60)` 单参数推进。脚本见 §6。

#### (a) 决定性:必须用单参数 `world.step(1/60)`

cannon-es 的 `step(dt, timeSinceLastCalled, maxSubSteps)` 在传了第二个参数时进入**累加器 + 墙钟**分支(`dist/cannon-es.js:12508-12551`;`internalStep()` 从 12553 行开始):

```js
if (timeSinceLastCalled === undefined) {
  this.internalStep(dt);          // 纯固定步:结果只由调用次数决定
  this.time += dt;
} else {
  this.accumulator += timeSinceLastCalled;
  const t0 = performance.now();
  let substeps = 0;
  while (this.accumulator >= dt && substeps < maxSubSteps) {
    this.internalStep(dt); this.accumulator -= dt; substeps++;
    if (performance.now() - t0 > dt * 1000) break;   // 慢机器上直接丢弃
  }
  this.accumulator = this.accumulator % dt;          // 余数被抹掉
  // ...再写 interpolatedPosition(渲染插值)
}
```

后果:同样的初始条件、同样的**墙钟时长**,帧率不同的机器实际执行的子步数不同。

要干净地测出这一点,场景里的摩擦必须关掉:这时 `x = 子步数 × (1/60) × v₀`,位置与子步数**严格成正比**——比例关系本身就是被测量的量,不是假象。实测(v₀ = 12 m/s,**无摩擦**平面,3 s 墙钟,解析位置 `12 × 3 = 36.000 m`;`exp.mjs` 的 §1.5(a)):

| 调用方式 | 帧率 | 实际子步数 `world.stepnumber` | `Δworld.time` | 位置 x | 与解析解之比 |
| --- | --- | --- | --- | --- | --- |
| `world.step(1/60, Δt, 3)` | 60 fps | 180 | 3.000 s | 36.000 m | 100% |
| `world.step(1/60, Δt, 3)` | 30 fps | 180 | 3.000 s | 36.000 m | 100% |
| `world.step(1/60, Δt, 3)` | 10 fps | 90 | 3.000 s | 18.000 m | **50%** |
| `world.step(1/60, Δt, 3)` | 5 fps | 45 | 3.000 s | 9.000 m | **25%** |
| `world.step(1/60)` × 180 次 | — | 180 | 3.000 s | 36.000 m(重复运行逐位一致) | 100% |

中间的"实际子步数"与"`Δworld.time`"两列都**不是由位置换算出来的**,而是运行结束后直接读的 `world` 字段(`world.stepnumber` 与 `world.time`,取前后差值——两者都是累计量,本表在场景搭建的 180 步**之后**才开始记录,所以读的是增量)。位置列仍保留是因为它与子步数严格成正比(`x = 子步数 × (1/60) × 12`),`exp.mjs` 现在逐行断言这个恒等式,而不是反过来拿 x 去证实子步数。

两列并排就说明了问题:60 fps 与 10 fps 走完同样的 3 s 墙钟,位置差了整整一倍,子步数是 180 对 90,而 `world.time` **两者都写着 3.000 s**——因为 `this.time += timeSinceLastCalled` 在走完累加器分支之后**无条件执行**,丢弃的子步并不会让它少走。也就是说引擎报的时间比它真正模拟的时间多,读时钟的游戏循环会以为物理已经推进到位——**它已经和真实模拟进度脱节**。(本表位置列的来历也说清楚:上一版这列填了带摩擦场景的 `0.7390 / 0.3710 / 0.1871`,它同样正比于子步数,却让人误以为那是"摩擦让箱子减速"的证据;摩擦会在同一个 3 s 窗口里加入与子步数无关的位移,两者混在一起就再也读不出来。)

**约束**:用 `world.step(1/60)`,由调用方(游戏循环或测试)自己决定每帧/每次运行推进几个子步,并把子步数当作**输入的一部分**记录;`world.time` 在三参数形式下会与实际模拟进度脱节,不能当计时器或断言依据。

#### (b) 摩擦的等效系数是**乘积** `μ_地面 × μ_角色`

`createFrictionEquationsFromContact`(`dist/cannon-es.js:10440-10489`)在两侧材质都带摩擦值时用乘积覆盖接触材质:

```js
let friction = cm.friction;
const matA = shapeA.material || bodyA.material;
const matB = shapeB.material || bodyB.material;
if (matA && matB && matA.friction >= 0 && matB.friction >= 0) {
  friction = matA.friction * matB.friction;   // 乘积,不是取某一侧
}
```

角色若不显式指定材质,会落到 `defaultContactMaterial.friction = 0.3`,等效摩擦被"打折"。实测(`exp.mjs` 的 §1.5(b),直接读 `world.frictionEquations[0].maxForce / |g|` 反解出等效 μ):

| 地面 μ | 角色材质 μ | `μ_g × μ_c` | 等效 μ(实测) | 读法 |
| --- | --- | --- | --- | --- |
| 0.05 | 1.00 | 0.0500 | **0.0500** | ✅ 等于乘积 |
| 0.90 | 1.00 | 0.9000 | **0.9000** | ✅ 等于乘积 |
| 0.05 | 0.30 | 0.0150 | **0.0150** | ✅ 等于乘积 |
| 0.90 | 0.30 | 0.2700 | **0.2700** | ✅ 等于乘积 |
| 0.05 | **0** | 0.0000 | **`n/a`** | ⚠️ 乘积为 0,`if (friction > 0)` 不成立,**根本没有摩擦方程**——两个面是无摩擦的 |
| 0.90 | **0** | 0.0000 | **`n/a`** | ⚠️ 同上 |
| 0.05 | **无 `Material`** | — | **0.3000** | ⚠️ 落回 `defaultContactMaterial`,地面参数被**完全忽略** |
| 0.90 | **无 `Material`** | — | **0.3000** | ⚠️ 同上 |
| **0** | **无 `Material`** | — | **0.3000** | ⚠️ 同上 |

三档地面值确实是**分别测**的(不是一次跑出来填三格):`exp.mjs` 的 §1.5(b) 用 `[0.05, 0.90, 0.0]` 各跑一遍,三行都读到 **0.3000**。

倒数第三、四行是这张表真正要警告的:角色只要漏挂 `Material`,**换地面材质对滑行距离完全没有影响**,关卡 2 的"冰面 vs 橡胶地"会静默退化成同一个场景。而"角色 μ 显式写 0"那一行是另一条路径:这时不是回落到 0.3000,而是**没有摩擦方程**——`n/a` 是"读不到任何摩擦系数",不是"摩擦系数为零"。两者在数值上都是无摩擦,但代码路径不同,`exp.mjs` 现在把这两种情况分开断言(乘积为 0 时断言"无摩擦方程",缺 `Material` 时断言恰好为 0.3000),上一版把它们一起短路成 `eff == null || …`,等于在这两个最关键的行上什么都没验。

**约束**:角色必须显式挂一个 `Material`,`friction = 1.0`,让"地面摩擦系数"就是设计值;`restitution` 同理(也是乘积)。

#### (c) 接触摩擦交付不了 μ 的对比:一个 240 倍的求解器冲量

同一函数的下一行:`mug = friction * (world.frictionGravity || world.gravity).length()` —— 上限来自**重力大小**,没有乘 `cosθ`,也不随法向力缩放,而且摩擦力沿两个切向各建了一个方程、各自带这个上限。

但**这个上限并不是实际起作用的那条**:摩擦方程装进 `GSSolver` 之后,第一步解出来的冲量就比库仑冲量 `μ_eff·g·dt` 大两个数量级。实测(角色材质 1.0,即等效 μ = 地面 μ,v₀ = 5 m/s,300 步 = 5 s;`exp.mjs` 的 §1.5(c)):

| 配置 | 冰面 μ=0.05 | 橡胶 μ=0.90 | 实测比 | 库仑理想比 |
| --- | --- | --- | --- | --- |
| **自由旋转**(出货配置),`iterations=10` | 1.0827 m | 1.0154 m | **1.07** | 18.0 |
| 自由旋转,`iterations=50` | 1.0819 m | 1.0149 m | 1.07 | 18.0 |
| `fixedRotation = true`,`iterations=10` | 0.0700 m | 0.0069 m | 10.07 | 18.0 |
| `fixedRotation = true`,`iterations=50` | 0.0700 m | 0.0069 m | 10.07 | 18.0 |

第一行是**出货配置**(§3.4 的角色会自由旋转,受击才可能翻滚),比值 **1.07,低于本卡自己的"≥3 倍"验收线**。原因在第一步就能看到:

```
step 0: Δvx = 1.96400 m/s   y = 0.5000   contacts = 4   (库仑冲量 μ_eff·g·dt = 0.00818)
```

`1.964 / 0.00818 ≈ 240`。求解器一次性拿走了 5 m/s 里的 1.96 m/s,而且这个冲量**带竖直分量**——箱子被弹离地面,随后 19 步 `world.contacts.length === 0`(空中),摩擦接触根本不存在。冰面与橡胶地的差别全靠落地后的那几步,于是 0.05 与 0.90 收敛到几乎同一个距离。**自由旋转的箱子测量的是碰撞恢复,不是摩擦。**

后两行那个 10.07 是**巧合而非对比度**:`fixedRotation` 下箱子没有任何自由度去"滚走",两步之内就被求解器的大冲量按死,两个表面都停在极小距离上,比值被两个小量相除放大。它同样**不随 `solver.iterations` 变化**(10 与 50 的差值在 m 的千分位,比值都读作 1.07;`fixedRotation` 两行的距离逐位一致)——所以本节末尾"已知限制"里"求解结果对迭代次数敏感"这条,在本场景**不成立**,上一版据此写进 §3.4 的"迭代次数必须写死"也失去了理由(仍然建议写死,理由是可复现性,不是敏感度)。

据此得到两条必须写进 #6 的结论:

1. `d = v₀² / (2μg)`(比值 = `μ_橡胶/μ_冰` = 18)只用于**选参数**;引擎自带的接触摩擦交付不了这个对比(出货配置实测 **1.07×**),摩擦必须由适配层显式施加(§1.5(d)),而且**验收断言必须测出来**,不能由公式推算。
2. `fixedRotation = true` 也不是解法:它把箱子按死在 0.07 m / 0.007 m,冰面上 5 m/s 的箱子 5 s 只走 **7 cm**,手感完全失真。这既不能用,也不能作为"省掉滚动"的开关。

#### (d) 适配层:显式库仑冲量,一下子把 18 倍和 `d ∝ v₀²` 都拿回来

做法是**两侧接触摩擦都置 0**,由适配层每步施加一个大小 ≤ `μ_地面 · g · dt` 的切向冲量(与 §1.4 推荐的"100–200 行适配层"是同一层):

```js
// 每步,推进之前:
const vt = body.velocity.dot(tangent) + predictSinTheta * G * DT   // 含重力在这一步将贡献的切向速度
const capacity = mu * G * normal.y * DT                            // 库仑冲量上限;normal.y 即 cosθ
const dv = Math.min(capacity, Math.abs(vt))                        // 上限保证一步之内不会反向
body.applyImpulse(tangent.scale(-Math.sign(vt) * dv), body.position)
```

`Math.min` 是关键:显式欧拉下不加这个夹取,物体会在停下之后被反向加速,得到"越走越回去"的假象。实测(`exp.mjs` 的 §1.5(d)):

| 模型 | v₀=2 | v₀=4 | v₀=8 | v₀=12 | `d(4)/d(2)` | 与解析解 `v₀²/(2μg)` 的偏差 |
| --- | --- | --- | --- | --- | --- | --- |
| 冰面 μ=0.05 适配层 | 4.057 m | 16.260 m | 65.106 m | 146.540 m | **4.008** | −0.41% / −0.20% / −0.10% / −0.07% |
| 橡胶 μ=0.90 适配层 | 0.210 m | 0.872 m | 3.554 m | 8.047 m | **4.154** | −7.23% / −3.66% / −1.83% / −1.22% |

- **偏差的符号是"走少了",不是"冲过头"**:八行偏差**全为负**,实测距离一致地**短于**解析值。这与上面的 `Math.min(capacity, |vt|)` 夹取是一致的——它存在的意义正是让停下的那一步不把速度推成反向,所以**不可能超调**。真正的机制是离散化的半步:冲量在 `world.step` **之前**施加,每一步的位移用的都是已经被削减过的速度,而解析积分用的是这一步的连续速度;两者之差恰好是第一步被削掉的那半个 `dt` 的速度对应的距离,即 `v₀·dt/2`。
- **这个绝对误差与 μ 无关,只与 `v₀` 成正比**:实测 `|d_实测 − d_解析|` = 0.0167 / 0.0333 / 0.0667 / 0.1000 m(冰面)与 0.0164 / 0.0332 / 0.0664 / 0.0997 m(橡胶),两种材质**在 3e-4 m 内重合**,且逐点等于 `v₀·dt/2 = v₀/120`。`exp.mjs` 的 §1.5(d) 现在直接打印这两列并断言二者之差 < 1e-3 m(实测残差 3.1e-4 m,来自橡胶行步数太少——v₀=2 只跑 13 步)。
- **18 倍只住在"相对"列里**:把绝对误差除以 `d_解析 = v₀²/(2μg)`,就得到表里的相对偏差,闭式为 `100·μ·g·dt/v₀` %——冰面 0.409 / 0.205 / 0.102 / 0.068,橡胶 7.365 / 3.683 / 1.841 / 1.228,**同一 `v₀` 处两行之比正好 18**。所以橡胶行"大一个量级"不是两行有不同的绝对误差,而是同一个绝对误差被短 18 倍的距离除出来的。上一版把这里写成"固定偏差 ÷ 增长的距离"并据此论证"模型是对的"——那个论证**无效**:1/`v₀` 的衰减只说明分子比 `v₀²` 低一阶,`|误差| ∝ v₀` 这类模型同样满足,不构成正确性证据。这一版改为直接给出上面的闭式 `d_实测 = d_解析 − v₀·dt/2` 并与实测两列对齐。对比度(下一条)用的是同一批 `d`,两行的相对偏差不同会**略微压低**对比度,所以 18.52× 是保守读数。
- **对比度**:冰面/橡胶 = **18.52×**(v₀=5)、**18.21×**(v₀=12),库仑理想 18.0。这正是 §1.5(c) 交付不了的那个量。
- **`d ∝ v₀²`**:`d(4)/d(2)` 实测 4.008(冰面)/ 4.154(橡胶),解析值 4.000。初速翻倍→距离四倍是**测出来的**,不再需要"接近 4 倍"这种措辞(关卡 3 的答案键因此有了实测支撑)。
- **地面尺寸**:`d_冰面(12 m/s) = 146.5 m`,所以**地面必须比它长**。§6.3 上一版写的 `Box(30, 0.5, 30)` 只够跑 30 m,箱子会在半途掉出地面——这也是 §1.5(c) 那些数字不可复现的原因之一。

#### (e) 坡道:适配层复现 `tanθ ≤ μ`,接触摩擦则永不下滑

同一个适配层接到斜面上就得到教科书结论。关键有两处:(1) 冲量上限里的法向分量用 `cosθ`,而不是 `|g|`;(2) 切向速度要算上**这一步重力即将贡献的那一份** `g·sinθ·dt`,否则每步都会漏掉一点速度,物体在最陡的坡上都"永不启动"。实测(`exp.mjs` 的 §1.5(e),5 s 静置 + 5 s 测量,位移取水平分量):

| 地面 μ | 真实释放角 `atan(μ)` | 适配层表现 |
| --- | --- | --- |
| 0.90 | 42.0° | 5°/15°/25°/30°/40° 位移 **0.000 m**;42° −0.082 m;44° **−12.531 m**;50° −44.440 m;60° −76.686 m |
| 0.30 | 16.7° | 5°/15° 位移 **0.000 m**;25° −50.360 m |
| 0.05 | 2.9° | 5° 就开始下滑(−13.715 m) |

阈值落在 `atan(μ)` 上,三档都对。相比之下**接触摩擦在 μ=0.9 的坡上,75°(tanθ = 3.73)仍不下滑**——这就是 §1.5(c) 那条"自由旋转只交付 1.07 倍"的同一个病根在斜面上的表现。所以坡道释放也必须走适配层,#6 的坡道角度可以直接按 `tanθ ≤ μ` 设计,**不需要**逐个角度手工标定。

但要注意前提:适配层必须知道**当前位置的法向**。平坦地面是 `(0,1,0)`,斜面是 `(−sinθ, cosθ, 0)`;角色在关卡 5 会同时遇到两者,#6 的适配层接口(§1.4 的 `step`)需要把法向作为每步输入而不是常量。

#### (f) 惯性、匀速直线、跳跃

| 现象(教学点) | 建模方式 | 怎么验证 |
| --- | --- | --- |
| 惯性:不受水平力时保持匀速直线运动 | 引擎刚体 + **显式把 `linearDamping` / `angularDamping` 置 0**(cannon-es 默认都是 `0.01`,不清零会得到"永远在减速"的错觉) | 无摩擦平面、无输入时连续 5 s,速度衰减 < 0.1%,方向偏角 < 0.1° |
| 匀速直线运动(合力为零) | 竖直方向重力与支持力由接触约束抵消,水平方向无外力 | 直道段位置误差在 5 s 内 < 1%(与解析解 `x = v₀t` 对比) |
| 速度越大越难停 | 由适配层的库仑冲量涌现:`μ` 固定时 `a = μg` 恒定,`d = v₀²/(2μg)` 自洽,不需要额外实现 | 固定子步数下,只改初速 2 → 4 m/s,滑行距离实测 **4.008 倍**(冰面)/ **4.154 倍**(橡胶),见 §1.5(d) |
| 跳跃与抛物线 | 引擎重力积分 | 跳跃远度与水平初速成正比 |
| **必须自写、不许偷懒的部分:角色控制层** | 输入只映射为**有限加速度**(并 clamp 最大加速度),**禁止直接 `body.velocity.set(...)`** | 若直接设速度,惯性直觉立刻消失:同一次"松手"在不同速度下都瞬间停下,关卡 3/4 的教学意图被破坏 |
| 决定性 | `world.step(1/60)` 单参数 + 自定义子步计数 + 关闭随机 | 同一子步数下两次运行结果**逐位一致**(见 (a) 实测) |

已知限制(交给 #6 记住):cannon-es 不建模滚动摩擦与空气阻力;**接触摩擦由 `GSSolver` 求解,首步冲量约为库仑冲量的 240 倍且带竖直分量,不构成一个可用的摩擦模型**(§1.5(c)),所以摩擦与坡道释放必须自写在适配层里;适配层每步需要一个**正确的接触法向**(平面 `(0,1,0)`,斜面 `(−sinθ, cosθ, 0)`),这是它相对"直接用引擎"多出来的唯一输入;**`cannon-es` 自 2022 年起没有新发布**,应把版本号写死并保留适配层。

### 1.6 被否决项的一句话理由

- **Babylon.js**:体积 2.5 倍,而它相对 Three.js 的增量能力(内置相机、GUI、Inspector、Node Material)对本项目的低多边形跑酷都不是瓶颈;V1/V2 双物理插件体系还会在 #6 引入不必要的决策。
- **Rapier**:工程上更优,但 1.11–1.58 MB gzip 的 wasm 与"打开即玩"冲突;保留为关卡数量/动态物体数量上升后的升级路径。
- **Ammo.js**:体积 1.56 MB 且无法 tree-shake,Emscripten API 样板多,维护节奏与 npm 脱节。
- **自写简化刚体**:平面场景够用,但无法低成本覆盖关卡 5 的"冰面 + 坡道 + 跳跃",性价比低于 36 KB 的 cannon-es。

## 2. 可借鉴案例及其可迁移设计

四个案例都不是"因为好玩"才被选中,而是各自解决了一个本项目会撞上的问题:怎么让力**可见**、怎么让失败**有信息量**、怎么让重试**没有心理成本**。

### 2.1 PhET Interactive Simulations(美国科罗拉多大学,免费中学物理交互模拟;参考「力和运动:基础」「斜坡:力和运动」)

它把力画出来:屏幕上每个物体带**实时力矢量箭头**,旁边跟**数值读数**和速度/加速度图;摩擦可以用滑块调,还能一键切到"冰面"场景;多个模拟内置**预测式提问**(先让学生猜,再运行)。

可迁移到本项目的设计:

- **HUD 可视化层**:角色头顶常驻"速度箭头 + 惯性条",把"我现在有多难停下来"变成可见量,而不是玩家的肌肉记忆。
- **参数旋钮**:通关后解锁摩擦/重力滑块,让学生自己复现现象(与 §3.2 的"自主感"对应)。
- **预测式提问**:PhET 用弹窗提问,本项目要改成**关卡内的动作**(§3.1 的"预判闸门"),避免打断跑酷节奏。

### 2.2 Poly Bridge / Bridge Constructor(桥梁建造沙盒)

循环是"设计 → 释放负载 → 看结果 → 改一处 → 再释放"。关键是**失败有具体归因**:构件应力用颜色梯度显示,先断的那根被高亮,而不是只告诉你"桥塌了";重试是秒级的,沙盒模式还取消了造价压力。

可迁移到本项目的设计:

- **失败点归因**:撞墙时高亮"接触点 + 那一刻的速度值",明确告诉学生"你是停不下来,不是跳得不够"。
- **秒级重试**:一键重来,重启 < 1 s,不做失败动画惩罚——与本项目"失败是物理后果,不是扣分"的定位一致。
- **双模式分层**:沙盒(自由实验,无目标)与挑战(星级)分离,对应本项目的"自由实验场 + 5 关卡"。

### 2.3 Sonic the Hedgehog 系列 / Super Mario 64 的冰面关(Ice Cap Zone / Cool, Cool Mountain)

商业跑酷游戏早就在用"摩擦系数"当关卡设计语言:冰面上加速与刹车距离显著变长,玩家必须**提前**做动作,否则就会滑出边缘或撞墙;速度感用镜头 FOV、音效与运动模糊放大。这里最有价值的一点是:**失败被视为理所当然的物理结果**,玩家不会觉得被惩罚,而是觉得"我早该想到"。

可迁移到本项目的设计:

- **地形即教具**:冰面/橡胶地用颜色 + 反光 + 脚步声区分,让学生不靠文字就能读出摩擦系数。
- **速度的体感化**:镜头 FOV 随速度线性拉伸 + 风声/脚步声加快,让"速度积累"变成紧张感,而不是数字。
- **无惩罚失败**:与 §2.2 的"秒级重试"合并执行,不设生命值/分数惩罚。

### 2.4 Algodoo(瑞典 Algoryx,面向中学课堂的 2D 物理沙盒)

它提供实时可改的重力/摩擦/阻尼、**慢动作回放**与**轨迹追踪**,教师在课堂上用它做"改一个参数,看结果怎么变"的探究。

可迁移到本项目的设计:

- **失败慢放**:撞墙瞬间 0.3× 慢放 1.5 s,让学生看清"不是操作慢了,是惯性没被抵消"。
- **幽灵轨迹**:显示上一次尝试的路径,失败原因和修正方向同时可见(§3.1 第 3 拍)。
- **探究式作业**:参数面板可作为延伸任务("把重力调成 3 m/s²,通关还能成立吗?"),把游戏寿命延长到课后。

## 3. MVP 玩法循环建议

### 3.1 "预判 → 行动 → 看结果 → 修正"的具体落地

| 拍 | 设计 | 必须遵守的约束 |
| --- | --- | --- |
| 1. 预判 | 关卡关键点前设"**预判闸门**":2 选 1 的快速选择(例:"冰面段会在 A 点还是 B 点停下?"),用画面内浮标 + 左右方向键/点击完成,选完立即继续跑 | 出现在动作前 ≤10 m 处;不弹窗、不暂停;必须选完才能通过闸门(强制进入"先想后做"的心智状态) |
| 2. 行动 | 跑酷操作只有三个动作:**向前加速**(按住)、**刹车/减速**(按住)、**跳跃**(单击),键位与手柄映射由 #6 定稿;输入只产生**有限加速度**并 clamp 上限 | 禁止直接设置速度;镜头、音效随速度线性增强 |
| 3. 看结果 | 停下/撞墙瞬间给出三组证据:(a) 实际滑行距离的**数轴读数(米)**与预判刻度同屏对比;(b) 上一次尝试的**幽灵轨迹**;(c) **0.3× 慢放 1.5 s** | 证据先于结算页出现;数值保留一位小数,避免"精确到厘米"的过度严谨 |
| 4. 修正 | 一键重试(≤1 次按键/点击),重启 < 1 s,保留幽灵轨迹与上一次预判选择 | 不扣资源、不播失败动画;结算文案指向"哪儿不一样",不指向"你错了" |

### 3.2 青少年玩家心理映射

| 心理需求 | 落地手段 | 可检查的指标 |
| --- | --- | --- |
| 即时反馈 | 任何输入到可见反馈 < 300 ms(音效/粒子/速度线);失败到可重试 < 1 s | 手动测 3 个关键动作 |
| 进度感 | 顶部 5 关进度条;每关 1–3 星(由"预判正确次数 + 尝试次数"决定);本地保存最佳滑行距离 | 刷新页面进度不丢(无后端,localStorage) |

### 3.3 5 关知识点排布(人教版八年级下册第 8 章「运动和力」)

| 关 | 名称 | 知识点 | 本关新引入的变量 | 玩家要做的事 | 过关判定 | 典型失败 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 起跑与刹车 | 8.1 力是改变物体运动状态的原因 | 摩擦力(单一橡胶地) | 加速到终点线前主动刹车,恰好停在目标区 | `\|x - x_目标\| ≤ 1.5 m` 且越线不超过 1.5 m | 冲过线 / 差一截没到 |
| 2 | 冰面还是橡胶地 | 8.3 摩擦力大小与接触面粗糙程度有关 | 路面材质(μ 切换) | 先选"哪一段滑得更远",再通过冰面段并在指定区停住 | 冰面段末端停在目标区 | 冰面上刹不住、撞墙 |
| 3 | 速度翻倍 | 8.1 力是改变物体运动状态的原因 + **滑行距离随速度增长得比速度更快**(`d ∝ v₀²`,**超出第 8 章范围的延伸**,层内做定性体验、不做公式推导) | 初速(加速时长) | 先回答"速度翻倍,那么滑行距离大约变成几倍?",再通关 | 答案键按**适配层实测**取值:选 "约 4 倍" 或 "(3.5, 4.5) 区间的任何整/半数",且实际距离落在目标区 | 低估滑行距离(选 2 倍,即以为距离与速度成正比) |
| 4 | 直着飞出去 | 8.1 惯性:物体保持原来的运动方向 | 弯道 / 断崖(方向变化) | 提前转向过弯,或故意利用惯性直线飞越缺口 | 落到对岸平台 | 撞弯道外壁 / 掉进缺口 |
| 5 | 综合路线 | 8.1 + 8.3 综合 | 组合(冰面 + 坡道 + 跳跃) | 一次跑完多段摩擦路线,中途 1 个预判闸门 | 全程 0 次越线失控 且 预测正确 ≥1 次 | 任一环节失控 |

设计原则:每一关只有**一个**新变量,其余参数与上一关一致;这样"结果变了"必然可以归因到"这个变量变了",教学因果链不会被多个变量污染。

> 用词提醒:惯性大小只由**质量**决定,与速度无关;速度变大改变的是"停下来需要的距离/时间",不是"惯性变大"。关卡 3 的知识点列必须按上表写法,不要写"惯性大小与速度有关"——那正是本关要纠正的错误直觉。
>
> 答案键提醒(上一版这里是硬编码的"4 倍"):`d ∝ v₀²` 是适配层库仑冲量的**推论**,不是可以任选的教学口号,所以答案键要用实测值兜底。`exp.mjs` 的 §1.5(d) 在固定子步数下只把初速从 2 改到 4 m/s,实测冰面 **4.008 倍**、橡胶 **4.154 倍**(解析值 4.000);测试断言落在 `[3.6, 4.4]` 内。另外 `d ∝ v₀²` 不在人教版八年级下册第 8 章的教学目标里(第 8 章讲"运动和力",运动学只到速度),所以本关按**定性延伸**处理:学生只需要观察到"距离涨得比速度多",不要求写出平方关系,必要时把"约 4 倍"的说法换成"明显超过 2 倍"。

## 5. 风险与开放问题(交给 #6 决策)

1. **cannon-es 维护停滞**(最后一次 npm 发布 2022-08-12,仓库最后 push 2024-01-06)。缓解:锁定精确版本号 + 物理适配层;若 #6 判断长期风险不可接受,升级到 Rapier 的代价是首屏 +1.11 MB gzip。
2. **引擎自带的接触摩擦不是一个可用的摩擦模型**(本卡最大的一条修正):出货配置下冰面 1.0827 m vs 橡胶 1.0154 m,比值 1.07,首步摩擦冲量约为库仑冲量的 240 倍、还带竖直分量把箱子弹到空中 19 步(§1.5(c))。#6 必须把摩擦搬到适配层(§1.5(d))。**如果照抄官方示例的 `ContactMaterial` 摩擦,关卡 2 会静默退化成"两种地面一样滑"。**
3. **步进与帧率解耦**:三参数 `step()` 在低帧率机器上会静默丢弃模拟步(5 fps 时 3 s 墙钟只跑 45 子步,见 §1.5(a))。若 #6 直接照搬官方示例的 `world.step(1/60, dt, 3)`,CI 上会出现"同一断言时通时不通"的 flaky 测试,学生之间也会得到不同的滑行距离。
4. **坡道必须靠适配层,不能靠引擎接触摩擦**:后者在 μ=0.9 的坡上 75° 仍不下滑(§1.5(e))。走适配层后阈值就回到 `tanθ ≤ μ`,关卡 5 的 15°–25° 设计可以直接用公式选角,再由测试断言释放/静止行为即可。代价是适配层每步要知道当前接触法向。
5. **低端设备性能**:桌面浏览器优先,但学校机房可能是集显。建议 #6 明确降级策略(默认关阴影/降低像素比/固定 30 FPS 选项);注意降帧率**不会**改变物理结果,只要用单参数步进。
6. **真实性与可玩性的冲突**:完全真实的摩擦会让学生"永远停不下来"。上限由 `μ` 和过关容差控制,教学文案不承诺"这是真实路面"。
7. **"直接设速度"的诱惑**:任何为了手感而直接给刚体赋值速度的实现,都会破坏本项目的核心教学意图,建议在 #6 写成硬约束。
8. **关卡数据格式**:地形段 / 摩擦系数 / 起点终点 / 过关判定 / 教学文案挂载点的 JSON schema 由 #6 定义;本卡只要求"摩擦系数与关卡内容解耦,加关卡不改引擎代码"。
9. **教学文案用词**:需要与学校教材口径一致(例如"惯性"只由质量决定,与速度无关,见 §3.3 的用词提醒)。建议人工/教师复核一次,这是唯一需要 human-in-the-loop 的点。

### 6.3 物理实测环境与脚本

**本卡的所有实测数字都由仓库里的 `docs/research/exp.mjs` 产出**,不是手算也不是复述:

```bash
mkdir -p /tmp/cannonlab && cd /tmp/cannonlab
npm init -y && npm i --no-audit --no-fund cannon-es@0.20.0
cp <repo>/docs/research/exp.mjs .
node exp.mjs             # 打印 §1.5(a)–(e) 与 §3.4 的全部测量值
node exp.mjs --assert    # 同一批测量值对上容差即 exit 0,否则 exit 1
```

脚本只有 `cannon-es` 一个依赖,常量全部固定在文件头部,不读环境变量、不写文件、不联网。

场景构造要点(与 §1.5 各表一一对应;上一版缺了这些常量,导致同一段文字可以被读出 1.08 m 到 795.84 m 四种滑行距离,这是 QA 复现不到本卡数字的直接原因):

- **角色位置与静置**:`HALF = 0.5`(真立方体 `Box(HALF, HALF, HALF)`),落地高度 `BODY_Y0 = HALF = 0.5`,先跑 `SETTLE_STEPS = 180` 步静置,再记录 `x₀` 并赋初速,测量 `MEASURE_STEPS = 300` 步。**任何滑行距离都指"静置后的位移"**,不是从出生点算起;
- **斜面就位**:半边长 `HALF` 的立方体绕 z 轴转 θ 后,质心到接触面沿法向 `n = (−sinθ, cosθ, 0)` 的距离是 `HALF × (|n_x| + |n_y|)`(θ=45° 时是 `0.5 × 1.414 = 0.707`,不是 `0.5`)。落座高度取 `0.5 + HALF × (|n_x| + |n_y|) + 0.002`。**上一版按 `HALF` 落座会把箱子埋进坡里**,求解器在第 0 步就以 9.19 m/s 的法向速度把它弹开,后续数字全部失真;
- **地面/斜面**:`mass = 0`;摩擦测试用足够长的 `Box`(见下),斜面用 `Box(30, 0.5, 30)` 加 `setFromEuler(0, 0, θ)`,都带显式 `Material`;
- **地面长度**:`d_冰面(12 m/s) = 146.540 m`,所以测量用的地面半长必须是 `GROUND_HALF_X ≥ 160 m`。**`Box(30, 0.5, 30)` 只够跑 30 m**,箱子会在半途掉出地面——这是本卡上一版 9.21 m / 1.23 m 那组数字不可复现的原因之一(§1.5(d));
- **角色**:`mass = 1`,`Box(0.5, 0.5, 0.5)`,带显式 `Material`(`friction` 取 1.0 或 0.3),`linearDamping = angularDamping = 0`;
- **推进**:`world.step(1/60)` 单参数,60 次/s;位置取 `body.position`,速度取 `body.velocity.length()`;
- **决定性对比(§1.5(a))**:同一场景分别以 60/30/10/5 fps 的 `Δt` 调用 `world.step(1/60, Δt, 3)`,对比 `world.stepnumber`(实际子步数)与最终位置。这一节**必须把摩擦关掉**,否则位置里混进了摩擦减速,比例关系看不出来;
- **适配层(§1.5(d)(e))**:两侧 `Material.friction` 都置 0,每步推进前施加库仑冲量 `min(μ × g × cosθ × dt, |v⁻_切向|)`,坡道上切向速度要含 `g·sinθ·dt` 这一项;
- 源码引用行号对应 `cannon-es@0.20.0` 的 `dist/cannon-es.js`(`step()` 12508-12551;`createFrictionEquationsFromContact()` 10440-10489)。两处行号与 `exp.mjs` 里引用的**同一对**范围已对齐(上一版卡片写 12507-12553 / 10448-10475,而 harness 写 12510-12549,同一个符号有两套范围,其中至少一套是错的;已按 v0.20.0 的 bundle 逐行核对)。

> 关于在 CI 里跑 `--assert`:本卡的 CI 是 Python-only(`python -m pytest tests/`),没有 Node 步骤。加一个 Node 步骤需要改 `.github/workflows/`,而本 issue 明确要求不动 CI,所以 `exp.mjs --assert` **在 CI 里不会被调用**,是可本地/手工运行的复现工具。上一版因此留下了一个真实的缺口:harness 可以被打坏(或改到数值全错)而测试套件仍然全绿——`tests/test_issue5_research_card.py` 只 grep 它的源码文本。
>
> 这一步的补救是在 Python 套件里加一个测试 `test_harness_runs_clean_when_node_and_deps_are_available`:它**真的执行** `node docs/research/exp.mjs --assert` 并断言 exit 0,但**在没有 `node`、或 `cannon-es` 无法解析时 `skip`**(用 `shutil.which("node")` 加一次 `import('cannon-es')` 探测),所以在当前 CI 上它是 skip 而不是失败,本地有 Node 环境时则是真门禁。这样 CI 行为没有变化(仍然不需要 Node 步骤),但"harness 从来没被执行过"不再是结构性事实:任何有 Node 的机器跑 `pytest` 都会真正跑一遍物理。
>
> 不过**光有"能跑通"还不够**,这一点是用变异测试查出来的:`exp.mjs` 里 §1.5(d) 原有的断言全是**定律**(倍增比落在 `[3.6, 4.4]`、对比度 ≥ 3×、地面长度上界),它们在 μ 被整体缩放时**不变**。把 `const ICE = 0.05` 改成 `0.07`(位移从 146.540 m 变成 104.643 m,对比度从 18.52× 变成 13.22×),harness 依然 exit 0——也就是说卡片公布的那些距离**没有任何东西在守**。现在 §1.5(d) 末尾补了三个把卡片单元格当字面期望的断言(`d_ice(12) = 146.540 m`、`d_rubber(12) = 8.047 m`、对比度 `18.52×`,容差 1 mm / 0.01×);同一个变异现在 exit 1 并指名 `d_ice(12) = 104.6425 m != card's 146.540 m`。**代价是卡片改了数字就得同步改这三行**——这是有意的:它们是卡片与实跑之间唯一一处硬绑定。
